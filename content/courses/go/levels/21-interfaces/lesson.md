# Интерфейсы — одно имя для разных типов

У вас уже есть типы с методами: прямоугольник умеет считать площадь, счётчик — увеличиваться. Но каждая функция пока прибита гвоздями к одному конкретному типу. Интерфейс (*interface*) снимает это ограничение: он описывает «умение», и функция начинает принимать ЛЮБОЙ тип, который это умеет. Это главный механизм абстракции в Go — и при этом на удивление компактный.

## Проблема: функция принимает только один тип

Заведём две фигуры. Обе умеют считать свою площадь (π живёт в пакете `math` — константа `math.Pi`):

```go
type Rect struct {
	W, H float64
}

func (r Rect) Area() float64 {
	return r.W * r.H
}

type Circle struct {
	R float64
}

func (c Circle) Area() float64 {
	return math.Pi * c.R * c.R
}
```

Теперь хотим функцию, которая красиво печатает площадь фигуры. Любой фигуры:

```go
func PrintArea(r Rect) {
	fmt.Printf("площадь: %.2f\n", r.Area())
}

PrintArea(Rect{W: 3, H: 4})   // площадь: 12.00
PrintArea(Circle{R: 1})       // ошибка компиляции: Circle — это не Rect
```

Круг не пролезает. Писать вторую `PrintCircleArea`, а потом третью для треугольника? Тела у них будут одинаковые до буквы — дублирование в чистом виде. Нужен способ сказать: «принимаю всё, что умеет `Area()`».

## Интерфейс: контракт из методов

```go
type Shape interface {
	Area() float64
}
```

Читается так: «`Shape` — это любой тип, у которого есть метод `Area() float64`». Сравните с уже знакомым `struct`: структура описывает, из каких **данных** состоит тип, а интерфейс — что тип **умеет делать**. Внутри интерфейса — только сигнатуры методов, без тел и без полей.

## Реализация — неявная

В Java или C# тип обязан объявить: «я реализую такой-то интерфейс». В Go ключевого слова `implements` нет вовсе. Тип реализует интерфейс **автоматически** — самим фактом наличия всех его методов. Это и называется неявной реализацией (*implicit implementation*).

Посмотрите ещё раз на `Rect` и `Circle`: у обоих есть метод `Area() float64` — значит, оба УЖЕ реализуют `Shape`. Мы не изменили в них ни строчки. Теперь чиним `PrintArea`:

```go
func PrintArea(s Shape) {
	fmt.Printf("площадь: %.2f\n", s.Area())
}

PrintArea(Rect{W: 3, H: 4})  // площадь: 12.00
PrintArea(Circle{R: 1})      // площадь: 3.14
```

Одна функция — любые фигуры. Появится треугольник с методом `Area() float64` — он тоже подойдёт, и трогать `PrintArea` не придётся.

> [!NOTE]
> Неявность — это суперсила: тип может реализовать интерфейс, о котором его автор даже не слышал. Ваша структура из сегодняшней задачи уже реализует десятки интерфейсов стандартной библиотеки — просто потому, что сигнатуры совпали.

## Интерфейсная переменная

Интерфейс — полноценный тип: можно объявить переменную и класть в неё значения разных конкретных типов:

```go
var s Shape

s = Rect{W: 2, H: 5}
fmt.Println(s.Area())          // 10

s = Circle{R: 2}
fmt.Printf("%.2f\n", s.Area()) // 12.57
```

Внутри интерфейсной переменной живёт пара: **конкретный тип + его значение**. Сначала там `(Rect, {2, 5})`, потом `(Circle, {2})`. При вызове `s.Area()` Go смотрит на конкретный тип внутри и зовёт именно его метод.

Важное следствие: через интерфейсную переменную видны ТОЛЬКО методы интерфейса.

```go
var s Shape = Rect{W: 2, H: 5}
fmt.Println(s.Area()) // ок: Area есть в контракте
fmt.Println(s.W)      // ошибка компиляции: у Shape нет поля W
```

> [!WARNING]
> Интерфейс — это «узкий обзор»: даже если внутри лежит `Rect`, поля `W` и `H` через `Shape` недоступны. Интерфейс знает про тип ровно то, что записано в контракте. Как вернуть себе конкретный тип — узнаете на уровне про type assertion.

## Слайс фигур: полиморфизм в действии

Раз `Shape` — тип, значит бывает и слайс `[]Shape`, где вперемешку живут разные фигуры:

```go
shapes := []Shape{
	Rect{W: 3, H: 4},
	Circle{R: 1},
	Rect{W: 1, H: 2},
}

total := 0.0
for _, s := range shapes {
	total += s.Area()
}
fmt.Printf("%.2f\n", total) // 17.14
```

На каждой итерации `s.Area()` уходит к «своему» типу: у прямоугольников считается произведение сторон, у круга — π·R². Один и тот же вызов ведёт себя по-разному в зависимости от того, что лежит внутри, — это и называют полиморфизмом (*polymorphism*).

## Интерфейс с несколькими методами

Методов в контракте может быть сколько угодно:

```go
type Shape interface {
	Area() float64
	Perimeter() float64
}
```

Правило строгое: тип должен иметь **все** методы интерфейса. Если у `Circle` есть `Area`, но нет `Perimeter`, — компилятор откажет прямо в месте присваивания:

```go
var s Shape = Circle{R: 1}
// ошибка: Circle does not implement Shape (missing method Perimeter)
```

Сообщение — подарок: Go называет и тип, и недостающий метод. Увидели `does not implement` — читайте, какого метода не хватает (или у какого совпало имя, но разошлась сигнатура).

## Нулевое значение интерфейса — nil

У интерфейсной переменной без значения внутри пусто — она равна `nil`:

```go
var s Shape
fmt.Println(s == nil) // true
s.Area()              // паника: invalid memory address or nil pointer dereference
```

Вызов метода на nil-интерфейсе роняет программу: Go не знает, чей метод звать — внутри нет ни типа, ни значения. Если интерфейсная переменная могла остаться пустой, сначала проверьте `if s != nil`.

## Указательный получатель и интерфейсы

С прошлых уровней вы помните: методы бывают у значения и у указателя. Для интерфейсов это важно:

```go
type Counter struct {
	value int
}

func (c *Counter) Inc() { // получатель-указатель
	c.value++
}

type Incrementer interface {
	Inc()
}

var a Incrementer = &Counter{} // ок: у *Counter метод Inc есть
var b Incrementer = Counter{}  // ошибка: Inc объявлен для *Counter, а не для Counter
```

Правило: методы с получателем-указателем принадлежат только типу `*T`. Поэтому если среди методов интерфейса есть указательные — кладите в интерфейсную переменную **адрес**: `&Counter{}`. Автовзятие адреса, которое выручало при обычных вызовах (`c.Inc()`), при упаковке в интерфейс не срабатывает.

## Маленькие интерфейсы — стиль Go

В других языках интерфейсы часто разрастаются на десятки методов. В Go принято наоборот — один-два метода:

```go
// Самый знаменитый интерфейс стандартной библиотеки:
type Reader interface {
	Read(p []byte) (n int, err error)
}
```

Логика простая: чем меньше методов требует интерфейс, тем больше типов смогут его реализовать — и тем шире применима каждая функция, принимающая его. С двумя героями этой философии — `fmt.Stringer` и `io.Reader`/`io.Writer` — вы познакомитесь на следующих уровнях.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| в интерфейсе `Area() float64`, у типа `Area() int` | тип НЕ реализует интерфейс: сигнатура должна совпадать целиком | выровнять типы: `Area() float64` |
| `s.W` через переменную типа `Shape` | ошибка компиляции: у интерфейса нет полей | добавить метод в контракт или работать с конкретным типом |
| `var s Shape; s.Area()` | паника: внутри интерфейса nil | сначала положить значение; проверять `s != nil` |
| `var i Incrementer = Counter{}` при `func (c *Counter) Inc()` | `does not implement` — указательный метод есть только у `*Counter` | класть адрес: `&Counter{}` |
| поле в интерфейсе: `type Shape interface { W float64 }` | ошибка компиляции: интерфейс описывает только методы | данные — в структурах, умения — в интерфейсах |

## Запомнить

- Интерфейс — контракт из методов: `type Shape interface { Area() float64 }`. Только сигнатуры, без полей и тел.
- Реализация неявная (*implicit*): есть все методы — тип уже реализует интерфейс, слово `implements` не нужно.
- Функция с параметром-интерфейсом принимает любой реализующий тип — это полиморфизм.
- Внутри интерфейсной переменной — пара (конкретный тип, значение); доступны только методы контракта.
- `[]Shape` — слайс, где вперемешку живут разные типы с общим умением.
- Нулевое значение интерфейса — `nil`; вызов метода на nil-интерфейсе — паника.
- Указательные методы входят в набор только `*T`: такие значения кладите в интерфейс через `&`.
- Идиома Go: интерфейсы маленькие, на 1–2 метода.
