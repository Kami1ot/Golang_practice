# Рекурсия — функция вызывает себя

Вы уже умеете писать функции, которые вызывают другие функции. Рекурсия (*recursion*) — следующий шаг: функция вызывает **саму себя**. Звучит как фокус с зеркалами, но это обычный рабочий инструмент. Некоторые задачи устроены как матрёшка: внутри большой задачи сидит точно такая же, только поменьше. Рекурсия просто честно повторяет это устройство в коде.

## Идея: задача внутри задачи

Возьмём обратный отсчёт от n до 1. Можно циклом, а можно рассуждать так: «напечатай n, а дальше — та же задача, но для n−1»:

```go
package main

import "fmt"

func Countdown(n int) {
	if n == 0 {
		fmt.Println("старт!")
		return
	}
	fmt.Println(n)
	Countdown(n - 1) // функция вызывает саму себя
}

func main() {
	Countdown(3)
}
```

Вывод:

```
3
2
1
старт!
```

Каждый вызов делает маленький кусочек работы (печатает одно число) и перекладывает остальное на следующий вызов — уже с задачей поменьше. На `n == 0` цепочка обрывается.

## Два обязательных ингредиента

У любой корректной рекурсии есть ровно два компонента — выучите их как таблицу умножения:

| Ингредиент | На какой вопрос отвечает | В `Countdown` |
|---|---|---|
| Базовый случай (*base case*) | Когда остановиться? | `n == 0` → печатаем «старт!» и выходим |
| Рекурсивный шаг (*recursive step*) | Как свести задачу к меньшей? | вызываем `Countdown(n - 1)` |

Порядок в коде почти всегда один и тот же: **сначала** проверка базового случая, **потом** рекурсивный шаг.

> [!WARNING]
> Уберите базовый случай — и функция будет вызывать себя, пока не кончится память под вызовы. Программа рухнет с переполнением стека (*stack overflow*): `runtime: goroutine stack exceeds 1000000000-byte limit`. Та же беда, если шаг «не туда»: напишите `Countdown(n)` вместо `Countdown(n - 1)` — базовый случай формально есть, но задача не уменьшается, и до остановки дело никогда не дойдёт.

## Факториал: раскручиваем стек вызовов

Классика жанра — факториал: n! = 1 · 2 · … · n, причём 0! = 1 по определению. Рекурсивное определение напрашивается само: n! = n · (n−1)!

```go
func Factorial(n int) int {
	if n == 0 {
		return 1 // базовый случай
	}
	return n * Factorial(n-1) // рекурсивный шаг
}
```

```go
fmt.Println(Factorial(5)) // 120
fmt.Println(Factorial(0)) // 1
```

Что происходит при вызове `Factorial(3)`? Каждый вызов замирает на умножении и ждёт результата вложенного вызова — получается «лесенка» вниз до базового случая и обратно вверх:

```
Factorial(3)
= 3 * Factorial(2)
= 3 * (2 * Factorial(1))
= 3 * (2 * (1 * Factorial(0)))
= 3 * (2 * (1 * 1))          ← дошли до базового случая
= 3 * (2 * 1)
= 3 * 2
= 6
```

Все незавершённые вызовы живут в стеке вызовов (*call stack*) — Go помнит, кто кого вызвал и кто чего ждёт:

| Шаг | Стек (слева — активный вызов) | Что происходит |
|---|---|---|
| 1 | `Factorial(3)` | ждёт результат `Factorial(2)` |
| 2 | `Factorial(2)` ← `Factorial(3)` | ждёт результат `Factorial(1)` |
| 3 | `Factorial(1)` ← `Factorial(2)` ← `Factorial(3)` | ждёт результат `Factorial(0)` |
| 4 | `Factorial(0)` ← три ждущих вызова | базовый случай: возвращает 1 |
| 5 | стек сворачивается обратно | 1 → 1·1 → 2·1 → 3·2 = 6 |

Глубина стека равна n: каждый незавершённый вызов занимает память. Для факториала это копейки, но о цене глубины полезно помнить с самого начала.

## Сумма цифр числа

Число тоже устроено как матрёшка. Два арифметических трюка, знакомых с уровня про типы: остаток `%` даёт последнюю цифру, целочисленное деление `/` — число без неё:

```go
fmt.Println(12345 % 10) // 5 — последняя цифра
fmt.Println(12345 / 10) // 1234 — всё, кроме последней
```

Значит, сумма цифр числа — это последняя цифра плюс сумма цифр «укороченного» числа. Базовый случай — однозначное число: его сумма цифр равна ему самому.

```go
func SumDigits(n int) int {
	if n < 10 {
		return n // однозначное число — базовый случай
	}
	return n%10 + SumDigits(n/10)
}
```

Раскрутка для 205:

```
SumDigits(205)
= 5 + SumDigits(20)
= 5 + (0 + SumDigits(2))
= 5 + (0 + 2)                ← 2 < 10, базовый случай
= 7
```

Заметьте: базовый случай `n < 10` покрывает и ноль — `SumDigits(0)` вернёт 0 без единого рекурсивного вызова.

## Рекурсия не только про числа

Матрёшки встречаются везде. Слайс — это «первый элемент + слайс поменьше», значит, сумму слайса тоже можно посчитать рекурсивно:

```go
func SumSlice(nums []int) int {
	if len(nums) == 0 {
		return 0 // пустой слайс — базовый случай
	}
	return nums[0] + SumSlice(nums[1:])
}
```

```go
fmt.Println(SumSlice([]int{3, 4, 5})) // 12
```

Знакомая срезка `nums[1:]` из уровня про слайсы отдаёт «всё, кроме первого» — и задача становится на один элемент меньше. Раскрутка:

```
SumSlice([3 4 5])
= 3 + SumSlice([4 5])
= 3 + (4 + SumSlice([5]))
= 3 + (4 + (5 + SumSlice([])))
= 3 + (4 + (5 + 0))          ← пустой слайс, базовый случай
= 12
```

Циклом `for range` это, честно говоря, проще. Но приём «первый + остальное» стоит запомнить: он дословно переносится на задачи, где цикл уже не спасает.

## Числа Фибоначчи: два базовых случая

Ряд Фибоначчи: 0, 1, 1, 2, 3, 5, 8, 13, … — каждое следующее число равно сумме двух предыдущих. Рекурсивная запись — прямо из определения:

```go
func Fib(n int) int {
	if n == 0 {
		return 0
	}
	if n == 1 {
		return 1
	}
	return Fib(n-1) + Fib(n-2)
}
```

```go
fmt.Println(Fib(10)) // 55
```

Здесь базовых случаев **два** — потому что рекурсивный шаг опирается на **два** предыдущих значения. Забудете про `n == 1` — `Fib(2)` вызовет `Fib(0)` и `Fib(1)`, а `Fib(1)` провалится в `Fib(0) + Fib(-1)`, дальше −2, −3… и привет, переполнение стека.

У этой красоты есть тёмная сторона. Нарисуем дерево вызовов для `Fib(5)`:

```
Fib(5)
├── Fib(4)
│   ├── Fib(3)
│   │   ├── Fib(2)
│   │   │   ├── Fib(1) = 1
│   │   │   └── Fib(0) = 0
│   │   └── Fib(1) = 1
│   └── Fib(2)
│       ├── Fib(1) = 1
│       └── Fib(0) = 0
└── Fib(3)
    ├── Fib(2)
    │   ├── Fib(1) = 1
    │   └── Fib(0) = 0
    └── Fib(1) = 1
```

`Fib(3)` честно пересчитан дважды, `Fib(2)` — трижды, и никто из вызовов не знает о работе соседей.

> [!NOTE]
> Число вызовов растёт **экспоненциально**: `Fib(30)` — уже примерно 2,7 миллиона вызовов (ещё мгновенно), а `Fib(40)` — около 330 миллионов, и программа заметно задумывается. Цикл считает то же самое за n шагов. Наивный рекурсивный Фибоначчи — отличный учебный пример и плохой рабочий код.

## Рекурсия или цикл?

Любую рекурсию можно переписать циклом — и наоборот. Тот же факториал без единого рекурсивного вызова:

```go
func FactorialLoop(n int) int {
	result := 1
	for i := 2; i <= n; i++ {
		result *= i
	}
	return result
}
```

Цикл не тратит стек и обычно работает быстрее. Что выбирать:

| Задача | Что читаемее |
|---|---|
| Линейный перебор: сумма слайса, счётчик, поиск максимума | Цикл |
| Задача «содержит сама себя»: факториал, сумма цифр | Дело вкуса; цикл экономнее |
| Деревья, вложенные структуры, «папка в папке в папке» | Рекурсия — циклом получится заметно сложнее |

Деревья и вложенные структуры ждут вас впереди в курсе — там рекурсия раскроется по-настоящему. Пока цель скромнее: научиться уверенно находить в задаче базовый случай и уменьшающий шаг.

> [!NOTE]
> В некоторых языках компилятор умеет превращать «хвостовую» рекурсию (*tail recursion* — когда рекурсивный вызов является самым последним действием функции) в цикл автоматически. Go так **не** делает: каждый рекурсивный вызов честно занимает место в стеке, каким бы «хвостовым» он ни был. Рассчитывать на эту оптимизацию в Go нельзя.

## Чек-лист: как придумать рекурсию

Перед тем как писать рекурсивную функцию, ответьте на три вопроса — по порядку:

1. **Какой самый маленький вход, ответ для которого известен сразу?** Это базовый случай: `n == 0`, `n < 10`, пустой слайс…
2. **Как выразить ответ через ответ для входа поменьше?** Это рекурсивный шаг: `n * Factorial(n-1)`, `n%10 + SumDigits(n/10)`…
3. **Каждый ли шаг приближает вход к базовому случаю?** Если да — рекурсия гарантированно остановится.

Проверим на новой задаче: повторить строку n раз (свой `strings.Repeat`).

```go
func RepeatString(s string, n int) string {
	if n == 0 {
		return "" // 1: ноль повторений — пустая строка, известно сразу
	}
	return s + RepeatString(s, n-1) // 2: одна копия + (n-1) копий
}
```

```go
fmt.Println(RepeatString("го", 3)) // гогого
```

Вопрос 3: аргумент `n` уменьшается на 1 каждый вызов и обязательно дойдёт до нуля — остановка гарантирована. Все три галочки на месте.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| Нет `if` с базовым случаем | бесконечные вызовы → *stack overflow* | первой строкой функции — условие остановки |
| `Factorial(n)` вместо `Factorial(n-1)` | шаг не уменьшает задачу → *stack overflow* | шаг обязан приближать к базовому случаю |
| У `Fib` один базовый случай вместо двух | `Fib(1)` уйдёт в отрицательные n и рухнет | шаг опирается на два значения — и случаев остановки два |
| Проверка базового случая ПОСЛЕ рекурсивного вызова | до проверки не дойдёт никогда | сначала остановка, потом шаг |
| `Fib(40)` наивной рекурсией «в бою» | секунды ожидания на ровном месте | цикл; про запоминание результатов — дальше в курсе |

## Запомнить

- Рекурсия (*recursion*) — функция вызывает саму себя; так удобно решать задачи-«матрёшки».
- Два обязательных ингредиента: базовый случай (*base case*) — когда остановиться, и рекурсивный шаг — как уменьшить задачу.
- Чек-лист из трёх вопросов: что известно сразу? как выразить через меньшее? уменьшает ли шаг задачу?
- Приём «первый + остальное» (`nums[0]` + `nums[1:]`) переносит рекурсию на слайсы и строки.
- Проверка базового случая идёт первой; шаг обязан приближать к ней, иначе — переполнение стека (*stack overflow*).
- Каждый незавершённый вызов занимает место в стеке: глубина рекурсии — это память.
- Шаг из двух вызовов (как у Фибоначчи) требует двух базовых случаев — и делает наивную версию экспоненциально медленной.
- Любую рекурсию можно переписать циклом; для линейных задач цикл чаще проще, для деревьев и вложенных структур рекурсия читается лучше.
- Go не оптимизирует хвостовую рекурсию — «бесплатной» глубины не бывает.
