# panic и recover — аварийный тормоз

Ошибки `error` — для ожидаемых неудач: файл не нашёлся, ввод кривой, сеть моргнула. Но бывают поломки другого сорта — **баги**: обращение за границу слайса, запись в неинициализированную карту. Для них у Go второй механизм — паника (*panic*). Этот уровень — про то, что паникует само, когда паниковать можно вручную, и как `recover` останавливает аварию. А главное — почему panic/recover это НЕ исключения из других языков.

## Что такое паника

Паника — аварийная остановка: программа печатает сообщение, стек вызовов и умирает.

```go
nums := []int{1, 2, 3}
fmt.Println(nums[5])
// паника: index out of range [5] with length 3
```

Классика runtime-паник, с частью которых вы уже сталкивались:

```go
var m map[string]int
m["ключ"] = 1        // паника: assignment to entry in nil map

var s Shape
s.Area()             // паника: nil-интерфейс — звать некого

x, y := 1, 0
fmt.Println(x / y)   // паника: integer divide by zero
```

Общее у них одно: это не «неудача», а **нарушение правил** — код попал в состояние, которого быть не должно.

## panic() вручную: только для невозможного

Панику можно поднять самому:

```go
func MustLoadConfig(path string) Config {
	cfg, err := load(path)
	if err != nil {
		panic("конфиг обязан существовать: " + err.Error())
	}
	return cfg
}
```

Когда это оправдано:

- **Невозможные состояния** — «сюда исполнение попасть не может, если код верен». Паника громко сообщит о баге вместо тихой порчи данных.
- **Инициализация при старте**: без конфига/шаблона программе всё равно не жить — лучше упасть сразу и громко. Конвенция имени — префикс `Must`: `regexp.MustCompile` из стандартной библиотеки паникует на кривом шаблоне.

Когда НЕ оправдано: всё остальное. Пользовательский ввод, файлы, сеть — это ожидаемые неудачи, для них `error`.

## Паника выполняет defer по дороге

Паника раскручивает стек — но обещания `defer` держатся (помните LIFO с уровня про defer?):

```go
func work() {
	defer fmt.Println("уборка выполнена")
	panic("всё пропало")
}
```

```
уборка выполнена
panic: всё пропало
```

Файлы закроются, замки отопрутся — `defer` выполняется даже на тонущем корабле. Именно на этом свойстве построен `recover`.

## recover: перехватить аварию

`recover()` останавливает панику — но работает **только внутри defer-функции**:

```go
func safe() (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("восстановлено: %v", r)
		}
	}()

	panic("сбой")
}

fmt.Println(safe())          // восстановлено: сбой
fmt.Println("программа жива") // программа жива
```

Разберём механику:

- Паника пошла раскручивать стек → выполнился defer → внутри него `recover()` вернул значение из `panic(...)` — и раскрутка ОСТАНОВИЛАСЬ.
- Если паники не было, `recover()` возвращает `nil` — поэтому проверка `if r != nil`.
- Значение паники имеет тип `any` (в панику можно передать что угодно) — глагол `%v` печатает его универсально.
- Именованный результат `err` (уровень про функции!) — единственный способ вернуть пойманное наружу: обычный `return` уже не выполнится.

Вызванный вне defer, `recover()` просто вернёт `nil` и никого не спасёт.

## Где recover уместен

Правильное место для `recover` — **граница системы**, за которой авария одной части не должна топить целое:

- веб-сервер ловит панику обработчика запроса: один запрос упал с 500-й ошибкой, остальные живут (кстати, раннер этой платформы защищён ровно так);
- пул воркеров ловит панику задачи, чтобы не потерять весь пул (встретится в секции про горутины).

Анти-паттерн — `recover` как замена `if err != nil`: «выбросим панику из глубины, поймаем наверху». Это и есть исключения, от которых Go сознательно отказался: поток управления становится невидимым. Паникуйте на багах, ловите на границах, всё остальное — честные `error`.

## Лучший recover — тот, что не понадобился

Почти каждую runtime-панику можно предвидеть дешёвой проверкой:

| Паника | Страховка |
|---|---|
| `index out of range` | проверить `len` перед обращением: `if len(nums) == 0 { return ..., err }` |
| `assignment to entry in nil map` | создавать карту: `m := map[string]int{}` или `make` |
| nil-интерфейс / nil-указатель | guard: `if s == nil { ... }` |
| `integer divide by zero` | проверить делитель: `if b == 0 { return 0, err }` |

Guard-проверка стоит одну строку и возвращает внятный `error`; паника стоит весь процесс.

## panic против error — итоговая таблица

| | `error` | `panic` |
|---|---|---|
| Что случилось | ожидаемая неудача | баг, невозможное состояние |
| Кто обрабатывает | вызывающий: `if err != nil` | никто (программа падает) или `recover` на границе |
| Видимость в сигнатуре | да: `(int, error)` | нет — тем и опасна |
| Примеры | файл не найден, кривой ввод | выход за границы, nil map |

Правило Go: **сомневаешься — возвращай error**. Паника — исключение, а не образ жизни.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| `panic("возраст отрицательный")` на пользовательском вводе | программа падает от опечатки в анкете | вернуть `error` — ввод пользователя всегда «ожидаемая неудача» |
| `r := recover()` в теле функции, не в defer | вернёт nil, паника летит дальше | только `defer func() { recover() }()` |
| `defer recover()` без функции-обёртки | значение теряется, панику формально глушит, но обработать нельзя | полная форма с `if r := recover(); r != nil` |
| recover везде «на всякий случай» | баги прячутся вместо того, чтобы чиниться | recover — только на границах системы |
| вернуть пойманное через обычный return | недостижимо: тело функции уже прервано | именованный результат: `func f() (err error)` |
| `panic(err)` вместо `return err` | вызывающий ждал error по договору, а получил аварию | пробрасывать через возврат |

## Запомнить

- Паника — аварийная остановка: сообщение, стек, смерть процесса. Runtime паникует сам: индекс за границей, запись в nil map, nil-интерфейс, деление на ноль.
- `panic(v)` вручную — только для багов и невозможных состояний; конвенция `Must*` — паника на инициализации.
- При раскрутке стека все `defer` выполняются.
- `recover()` работает только внутри defer-функции: возвращает значение паники или nil.
- Вернуть пойманное наружу — через именованный результат `(err error)`.
- Место recover — граница системы (обработчик запроса, воркер), а не замена `if err != nil`.
- Почти любую панику дешевле предвидеть guard-проверкой, чем ловить.
- Сомневаешься — возвращай `error`.
