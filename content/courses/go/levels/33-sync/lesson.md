# Гонки данных и sync.Mutex — почему счётчик врёт

Мы дважды обходили эту тему стороной: на уровне про горутины раздавали каждому «свой слот», на уровне про каналы передавали значения по трубе. Пора посмотреть врагу в лицо: что именно ломается, когда две горутины трогают одну переменную, — и как чинить это замком (*mutex*).

## Эксперимент: тысяча инкрементов

Тысяча горутин, каждая прибавляет единицу к общему счётчику:

```go
counter := 0

var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		counter++ // тысяча горутин долбят одну переменную
	}()
}
wg.Wait()
fmt.Println(counter) // 962?! 987?! Каждый запуск — новое число ≤ 1000
```

Программа компилируется, не паникует — и **врёт**. Почему? `counter++` — это не одна операция, а три: прочитать значение, прибавить единицу, записать обратно. Две горутины читают одновременно (обе видят 41), обе прибавляют (обе получают 42), обе записывают — одна из единиц потеряна. Это гонка данных (*data race*): итог зависит от того, кто успел раньше.

> [!WARNING]
> Гонка — худший вид бага: она невоспроизводима. На вашей машине «работает», у пользователя раз в неделю теряет данные. Правило Go простое: если к переменной обращается больше одной горутины и хотя бы одна ПИШЕТ — нужна синхронизация. Без исключений «тут всего одна строчка».

## Детектор гонок

Go умеет ловить гонки на лету — флаг `-race`:

```
go run -race main.go
go test -race ./...
```

При обнаружении печатается `WARNING: DATA RACE` со стеками обеих горутин — какая читала, какая писала. Медленнее обычного запуска в разы, поэтому включают его в тестах и отладке, а не в бою. Привыкайте гонять конкурентный код с `-race` — детектор находит то, что глазами не увидеть.

## sync.Mutex: замок на дверь

Мьютекс (*mutex*, от *mutual exclusion* — взаимное исключение) пускает к данным только одну горутину за раз:

```go
var (
	mu      sync.Mutex
	counter int
)

for i := 0; i < 1000; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		mu.Lock()   // запираем дверь
		counter++   // внутри — только мы
		mu.Unlock() // отпираем
	}()
}
wg.Wait()
fmt.Println(counter) // 1000. Всегда 1000.
```

`Lock()` захватывает замок; если он уже захвачен другой горутиной — ждёт своей очереди. `Unlock()` освобождает. Код между ними называют критической секцией (*critical section*): в ней гарантированно находится не больше одной горутины.

Идиома для функций посложнее — `defer`:

```go
mu.Lock()
defer mu.Unlock() // отопрётся при любом выходе — даже при панике
// ...критическая секция любой сложности...
```

## Потокобезопасный тип: мьютекс + данные

Правильный дом для мьютекса — структура, рядом с данными, которые он охраняет:

```go
type SafeCounter struct {
	mu sync.Mutex
	n  int
}

func (c *SafeCounter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func (c *SafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}
```

Три детали, каждая важна:

- поля не экспортированы: снаружи только методы — забыть про замок невозможно;
- получатели указательные (`*SafeCounter`): методы меняют состояние, а главное — **мьютекс нельзя копировать** (копия — отдельный замок, охраняющий воздух);
- читающий `Value` тоже берёт замок: чтение во время чужой записи — такая же гонка.

## WaitGroup под микроскопом

`WaitGroup` вы используете с уровня про горутины — закрепим правила, о которые спотыкаются:

- `Add` — в запускающей горутине, ДО `go`. Add изнутри горутины — гонка с `Wait`;
- `Done` — через `defer` первой строкой горутины: выполнится даже при панике;
- счётчик не должен уходить в минус (лишний Done — паника `negative WaitGroup counter`);
- `WaitGroup`, как и мьютекс, не копируется: в функции передавайте `*sync.WaitGroup` (а лучше — не передавайте вовсе: пусть живёт в замыкании).

## Мьютекс или канал?

Оба решают проблему разделяемого состояния — по-разному:

| Ситуация | Инструмент |
|---|---|
| охраняем состояние: счётчик, карту, кэш | мьютекс — коротко и по делу |
| передаём данные из горутины в горутину | канал — владение уезжает вместе со значением |
| поток задач/результатов, конвейер | каналы + select |
| «жду, пока все закончат» | WaitGroup |

Девиз «разделяйте память через общение» — про архитектуру: крупные потоки данных лучше гонять каналами. Но для маленького общего состояния мьютекс проще и быстрее — и это тоже идиоматичный Go. Инженерное правило: **выбирайте то, что проще читается**.

> [!NOTE]
> В пакете `sync` есть и другие инструменты: `RWMutex` (много читателей ИЛИ один писатель — для данных, которые читают часто, а пишут редко), `Once` (выполнить ровно один раз), `atomic` (безблокировочные счётчики). Начните с Mutex и WaitGroup — остальное подключится по мере надобности.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| `counter++` из многих горутин без замка | потерянные обновления, каждый запуск — новое число | мьютекс вокруг критической секции |
| `Lock` без `Unlock` (ранний return из середины) | следующая горутина ждёт вечно: deadlock | `defer mu.Unlock()` сразу после Lock |
| `Value()` читает без замка «это же только чтение» | чтение во время записи — тоже гонка | замок и на чтение (или RWMutex) |
| копирование структуры с мьютексом | копия охраняется ДРУГИМ замком — защиты нет | методы и передача через указатель |
| `mu.Lock(); mu.Lock()` в одной горутине | самоблокировка: Go-мьютекс не реентерабелен | одна критическая секция — один Lock |
| конкурентная запись в `map` без замка | паника: concurrent map writes | карта + мьютекс в одной структуре |

## Запомнить

- Гонка данных: ≥2 горутин обращаются к переменной, хотя бы одна пишет, синхронизации нет. Итог непредсказуем.
- `counter++` — три операции; параллельные инкременты теряются.
- Детектор: `go test -race` / `go run -race` — гоняйте конкурентный код с ним.
- `sync.Mutex`: `Lock()` → критическая секция → `Unlock()`; идиома — `defer mu.Unlock()`.
- Мьютекс живёт в структуре рядом с данными; методы — с указательным получателем; чтение тоже под замком.
- Мьютексы и WaitGroup не копируются — только указатели.
- WaitGroup: Add до go, Done через defer, счётчик не уходит в минус.
- Состояние — мьютекс, поток данных — каналы; выбирайте то, что читается проще.
