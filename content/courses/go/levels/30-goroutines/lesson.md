# Горутины — конкурентность за одно слово

Всё, что вы писали до сих пор, выполнялось строго по очереди: строка за строкой, вызов за вызовом. Пришло время суперспособности, ради которой Go часто и выбирают: горутины (*goroutines*) — лёгкие потоки выполнения, которые работают одновременно. Запускаются они одним словом `go`, а вот ДОЖДАТЬСЯ их — целая наука, с которой мы сегодня и разберёмся.

## Конкурентность: зачем это вообще

Программа скачивает три файла. Последовательно: скачали первый, потом второй, потом третий — время складывается. А ведь ожидание сети — это именно ожидание: процессор скучает. Конкурентность (*concurrency*) позволяет вести несколько дел «параллельно»: пока одно ждёт, другое работает. В Go это делается настолько просто, что конкурентный код выглядит почти как обычный.

## Ключевое слово go

Поставьте `go` перед вызовом функции — и она запустится в отдельной горутине:

```go
func sayHello() {
	fmt.Println("привет из горутины!")
}

func main() {
	go sayHello() // не ждём завершения — летим дальше
	// ...main продолжает свои дела...
}
```

`go sayHello()` не блокирует: main мгновенно переходит к следующей строке, а `sayHello` выполняется «где-то рядом». Кстати, `main` — тоже горутина, самая первая: её запускает сам Go при старте программы.

Чаще всего с `go` запускают анонимные функции (привет, уровень про замыкания):

```go
go func() {
	fmt.Println("анонимная горутина")
}()
```

Обратите внимание на `()` в конце — функцию нужно не только объявить, но и вызвать.

## Главная ловушка: main никого не ждёт

Попробуем «в лоб»:

```go
func main() {
	go fmt.Println("привет из горутины")
	fmt.Println("main завершился")
}
```

Скорее всего, вы увидите только `main завершился`. Когда функция `main` доходит до конца, **программа завершается целиком** — вместе со всеми горутинами, где бы они ни находились. Никто никого не ждёт: main закончился — свет выключили.

В учебниках эту проблему часто «решают» костылём:

```go
go fmt.Println("привет из горутины")
time.Sleep(100 * time.Millisecond) // подождём 100 миллисекунд... наверное, хватит?
```

`time.Sleep` из пакета `time` просто усыпляет текущую горутину (про пакет `time` подробно — в следующей секции). Для экспериментов сойдёт, но в настоящем коде это мина: 100 миллисекунд может не хватить, а если хватило — программа зря простаивает. Нужен способ дождаться **точно**.

## sync.WaitGroup: честное ожидание

Группа ожидания (*wait group*) из пакета `sync` — счётчик незавершённых дел:

```go
func main() {
	var wg sync.WaitGroup

	wg.Add(1) // план: одно дело
	go func() {
		defer wg.Done() // дело сделано — минус один
		fmt.Println("из горутины")
	}()

	wg.Wait() // стоим, пока счётчик не обнулится
	fmt.Println("из main")
}
```

```
из горутины
из main
```

Три метода — весь API:

- `wg.Add(n)` — увеличить счётчик: «запланировано ещё n дел». Вызывается **до** запуска горутины, в запускающем коде.
- `wg.Done()` — уменьшить на один: «одно дело завершено». Идиома — через `defer` первой строкой горутины: выполнится даже при панике (уровень 29 в действии).
- `wg.Wait()` — заблокироваться, пока счётчик не станет нулём.

Теперь порядок гарантирован: `из main` печатается строго после горутины — `Wait` не пропустит.

> [!WARNING]
> `wg.Add(1)` должен выполниться ДО `go ...`, в запускающей горутине. Если написать `Add` внутри самой горутины, возможна беда: main добежит до `Wait` раньше, чем горутина успеет заявить о себе, — счётчик нулевой, `Wait` пропускает, программа завершается. Правило: планируем снаружи, отчитываемся внутри.

## Запускаем пачку горутин

Классика — горутина на каждый элемент:

```go
var wg sync.WaitGroup

for i := 1; i <= 3; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("работник", i)
	}()
}
wg.Wait()
```

```
работник 3
работник 1
работник 2
```

Два наблюдения. Первое: **порядок непредсказуем** — горутины выполняются как успеют, и от запуска к запуску вывод меняется. Это нормально и правильно: раз дела независимы, порядок не обещан. Второе: каждая горутина видит «свой» `i` — начиная с Go 1.22 переменная цикла создаётся заново на каждой итерации.

> [!NOTE]
> В коде до Go 1.22 вы встретите наследие старых времён: `go func(i int) { ... }(i)` — переменную цикла передавали параметром, потому что раньше все горутины делили ОДНУ переменную `i` и часто печатали «4 4 4». Сейчас это не нужно, но передача параметром по-прежнему работает и отлично читается — в задачах пользуйтесь на здоровье.

## Горутины дёшевы

Горутина — не поток операционной системы: она стартует с пары килобайт стека, и Go сам распределяет тысячи горутин по ядрам процессора. Запустить 10 000 горутин — обычное дело, а не подвиг. Поэтому в Go не экономят: горутина на запрос, горутина на файл, горутина на подзадачу.

При этом настоящая параллельность (*parallelism* — несколько дел строго в один момент времени на разных ядрах) — забота рантайма: вы описываете конкурентность, Go раскладывает её по ядрам.

## Паника в горутине — смерть всей программы

Урок про panic предупреждал: recover ловит панику только в СВОЕЙ горутине. Если горутина запаниковала и внутри неё некому вызвать recover — падает вся программа, каким бы аккуратным ни был main:

```go
go func() {
	panic("авария в горутине") // программа умрёт целиком
}()
```

Отсюда практика: код горутины, которому вы не доверяете, оборачивают в защиту с recover — вроде функции `Protect` из задачи прошлого уровня.

## Как получить результат?

Заметили, что все примеры только печатают? Это не случайно. Вернуть значение из горутины через `return` некуда — вызывающий давно убежал вперёд. Писать результат в общую переменную — опасно (почему — узнаете на уровне про гонки данных). Единственный по-настоящему безопасный способ из сегодняшнего арсенала — дать каждой горутине **свой** слот:

```go
nums := []int{3, 5, 7}
res := make([]int, len(nums)) // по слоту на горутину

var wg sync.WaitGroup
for i, n := range nums {
	wg.Add(1)
	go func(i, n int) {
		defer wg.Done()
		res[i] = n * n // каждая пишет ТОЛЬКО в свой res[i]
	}(i, n)
}
wg.Wait()
fmt.Println(res) // [9 25 49]
```

Разные горутины — разные ячейки слайса, конфликтов нет. А правильный универсальный ответ на вопрос «как горутинам общаться» — каналы — ждёт вас на следующем уровне.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| `go doWork()` в конце main без ожидания | горутина не успевает: main завершился — программа умерла | `sync.WaitGroup`: Add → Done → Wait |
| `time.Sleep` вместо ожидания | то не хватает, то пересыпаем — недетерминизм | WaitGroup ждёт ровно столько, сколько нужно |
| `wg.Add(1)` внутри горутины | Wait может проскочить раньше Add — программа завершится досрочно | Add — до `go`, в запускающем коде |
| забыли `wg.Done()` | Wait ждёт вечно: deadlock | `defer wg.Done()` первой строкой горутины |
| `go func() {...}` без `()` | ошибка компиляции: функцию нужно вызвать | `go func() {...}()` |
| полагаться на порядок вывода горутин | от запуска к запуску порядок разный | не полагаться; нужен порядок — свои слоты или каналы |

## Запомнить

- `go f()` запускает функцию в отдельной горутине и НЕ ждёт её; main — тоже горутина.
- main завершился — программа умерла вместе со всеми горутинами.
- Ожидание: `sync.WaitGroup` — `Add(1)` до запуска, `defer wg.Done()` внутри, `Wait()` в конце.
- Порядок выполнения горутин не гарантирован — и это нормально.
- Горутины дёшевы: тысячи — обычное дело.
- Паника в горутине без своего recover роняет всю программу.
- Безопасно собирать результаты — по своему слоту `res[i]` на горутину; универсальный способ (каналы) — на следующем уровне.
