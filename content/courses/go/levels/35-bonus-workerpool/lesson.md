# Пул воркеров — конкурентность с бюджетом

«Горутина на задачу» — прекрасно, пока задач сотня. А если миллион, и каждая ходит в сеть или грузит процессор? Миллион одновременных запросов положит и вашу программу, и чужой сервер. Решение — пул воркеров (*worker pool*): фиксированная бригада из K горутин разбирает очередь из N задач. Это самый известный паттерн конкурентного Go — и отличная возможность собрать вместе всё, что вы выучили в этой секции.

## Идея: очередь и бригада

Всё строится из знакомых деталей:

- **канал задач** — очередь: производитель кладёт задачи и закрывает канал;
- **K воркеров** — одинаковые горутины: `for job := range jobs { ... }` — каждая берёт следующую свободную задачу;
- **WaitGroup** — дождаться, пока бригада закончит.

Канал здесь работает распределителем сам по себе: два воркера никогда не получат одну задачу — приём из канала атомарен. Никаких «менеджеров» и разруливания вручную.

## Скелет пула

```go
func pool(jobs []int, workers int) {
	jobsCh := make(chan int)

	var wg sync.WaitGroup
	for w := 0; w < workers; w++ { // бригада из K одинаковых воркеров
		wg.Add(1)
		go func() {
			defer wg.Done()
			for job := range jobsCh { // берём задачи, пока очередь не опустеет
				process(job)
			}
		}()
	}

	for _, j := range jobs { // производитель: кладём все задачи...
		jobsCh <- j
	}
	close(jobsCh) // ...и объявляем: больше не будет

	wg.Wait() // ждём, пока бригада доделает
}
```

Проследите жизненный цикл: воркеры стартуют и виснут на пустом канале → производитель закидывает задачи, воркеры их разбирают → `close` заставляет `range` в каждом воркере завершиться, как только канал опустеет → `Wait` отпускает главную горутину. Ни одного `Sleep`, ни одной гонки.

> [!NOTE]
> Сколько воркеров брать? Для процессорных задач — примерно по числу ядер: `runtime.NumCPU()`. Для задач с ожиданием (сеть, диск) — больше: пока одни ждут ответа, другие работают. Точное число подбирают экспериментом; важно, что оно ФИКСИРОВАНО и не растёт с числом задач.

## Собираем результаты: слоты против канала

Если задачи возвращают значения, есть два честных способа их собрать. Первый вы знаете с уровня про горутины — **слоты по индексу**:

```go
func Process(nums []int, workers int, f func(int) int) []int {
	res := make([]int, len(nums))
	idx := make(chan int) // очередь ИНДЕКСОВ

	var wg sync.WaitGroup
	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := range idx {
				res[i] = f(nums[i]) // каждый индекс достаётся одному воркеру
			}
		}()
	}

	for i := range nums {
		idx <- i
	}
	close(idx)
	wg.Wait()
	return res
}
```

Хитрость: по каналу ездят не сами задачи, а **индексы** — воркер и читает вход, и пишет результат в свою ячейку. Порядок результатов совпадает со входом бесплатно, мьютекс не нужен: разные индексы — разные ячейки.

Второй способ — **канал результатов**: воркеры шлют ответы в общий канал, кто-то их собирает. Он нужен, когда результаты обрабатывают потоково, не дожидаясь всех. Но есть тонкость: канал результатов надо закрыть, когда ВСЕ воркеры закончат, — и делает это отдельная горутина:

```go
results := make(chan int)

go func() {      // закрывальщик
	wg.Wait()    // дождаться бригаду...
	close(results) // ...и только потом закрыть выход
}()

for r := range results { // главная горутина спокойно собирает
	fmt.Println(r)
}
```

Закрыть `results` прямо в воркере нельзя — их K штук, а закрывать канал можно один раз. Закрыть до `Wait` — потерять недосланные результаты. Горутина-«закрывальщик» — стандартное решение.

## Когда пул, а когда просто горутины

| Ситуация | Подход |
|---|---|
| задач немного, каждая лёгкая | горутина на задачу + WaitGroup — пула не надо |
| задач много / внешние ресурсы не резиновые | пул: фиксированные K воркеров |
| поток задач бесконечен (сервер) | пул воркеров, живущий всю программу, + context для остановки |

Пул — это про **ограничение**: вы явно назначаете степень параллельности вместо «сколько получится». Добавьте context с прошлого уровня — и бригаду можно вежливо распустить посреди смены.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| забыли `close(jobsCh)` | воркеры вечно ждут задач: deadlock после Wait | close после последней отправки |
| `close` канала результатов в воркере | паника: close закрытого канала (их же K штук) | отдельная горутина: Wait → close |
| воркеры пишут в общий слайс через `append` | гонка данных: append не потокобезопасен | слоты по индексу или мьютекс |
| запускать горутину на задачу «внутри пула» | пул перестал ограничивать — вернулись к миллиону горутин | воркеры сами берут задачи из канала |
| `wg.Add(len(jobs))` вместо `wg.Add(workers)` | счётчик не сойдётся с числом Done — зависание или паника | считаем ВОРКЕРОВ, а не задачи |

## Запомнить

- Пул воркеров = канал задач + K одинаковых горутин с `for job := range jobs` + WaitGroup.
- Канал сам распределяет задачи: одна задача — один воркер, гонок нет.
- Производитель закрывает канал задач — range у воркеров завершается сам.
- Результаты: слоты по индексу (порядок бесплатно) или канал результатов (закрывает отдельная горутина после Wait).
- K фиксировано: по ядрам для вычислений, больше — для ожидания сети/диска.
- Пул — это осознанное ограничение параллельности, а не её максимум.
