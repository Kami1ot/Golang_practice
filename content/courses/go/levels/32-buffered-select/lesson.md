# Буферы и select — гибкое общение

Каналы прошлого уровня были строги: отправка ждёт приёмника, приём ждёт отправителя, всё по рандеву. Сегодня два инструмента, снимающих эту жёсткость: буферизованные каналы (*buffered channels*) — очередь с запасом места, и оператор `select` — умение ждать несколько каналов одновременно (или не ждать вовсе).

## Буферизованный канал: очередь с местами

Второй аргумент `make` задаёт ёмкость буфера:

```go
ch := make(chan int, 3) // буфер на три значения
```

Правила блокировки смягчаются:

- **отправка** не блокирует, пока в буфере есть место; блокирует — когда буфер полон;
- **приём** не блокирует, пока в буфере есть значения; блокирует — когда пуст.

```go
ch := make(chan int, 2)
ch <- 1 // легло в буфер, никто не ждёт
ch <- 2 // легло в буфер
// ch <- 3 — а вот это уже заблокируется: буфер полон

fmt.Println(<-ch) // 1 — порядок FIFO: первым пришёл, первым ушёл
fmt.Println(<-ch) // 2
```

Помните deadlock из прошлого урока — `ch <- 1` в одиноком main? С буфером `make(chan int, 1)` тот код работает: значение ложится в буфер, встреча с приёмником не нужна.

У канала есть длина и ёмкость — как у слайса:

```go
ch := make(chan int, 3)
ch <- 10
ch <- 20
fmt.Println(len(ch), cap(ch)) // 2 3 — занято два места из трёх
```

## Зачем нужен буфер

Буфер развязывает отправителя и приёмника по времени: производитель может убежать вперёд, пока потребитель разгребает. Типичные применения:

- **известное число результатов**: N горутин шлют по одному значению в `make(chan T, N)` — ни одна не заблокируется, даже если собирать результаты начнут позже;
- **сглаживание всплесков**: производитель работает рывками, потребитель — ровно;
- **сигналы**: `make(chan struct{}, 1)` — «звонок», который можно нажать, не дожидаясь, пока откроют.

> [!WARNING]
> Буфер — не лекарство от deadlock, а отсрочка: полный буфер блокирует так же, как небуферизованный канал. Если потребителя нет вовсе, буфер лишь оттянет зависание на cap отправок. Выбирайте размер из логики задачи (например, «ровно N результатов»), а не «поставлю 1000 на всякий случай».

## select: ждать несколько каналов

Горутина обслуживает два источника: сообщения и сигнал остановки. Читать по очереди нельзя — застрянем на первом, пока второй молчит. Нужен `select`:

```go
select {
case msg := <-messages:
	fmt.Println("сообщение:", msg)
case <-quit:
	fmt.Println("выходим")
	return
}
```

`select` похож на `switch`, но ветки — операции с каналами. Он ждёт, пока хотя бы одна операция станет возможной, и выполняет её ветку. Правила:

- готова одна ветка — выполняется она;
- готовы несколько — выбирается **случайная** из готовых (честность: ни один канал не голодает);
- не готова ни одна — `select` блокируется до первой готовой.

Выполняется ровно ОДНА ветка за один проход — «обслуживать вечно» означает `for` вокруг `select`.

## default: не ждать вовсе

Ветка `default` выполняется, если ни одна операция не готова прямо сейчас, — `select` перестаёт блокировать:

```go
select {
case v := <-ch:
	fmt.Println("получили", v)
default:
	fmt.Println("канал пуст, идём дальше")
}
```

Это неблокирующие операции: «проверь, но не жди». Так делают неблокирующую отправку (попробовать положить, а если полно — не стоять), неблокирующий приём и опрос нескольких источников на лету.

```go
// неблокирующая отправка:
select {
case ch <- v:
	// удалось
default:
	// буфер полон — решаем, что делать: выбросить, посчитать, залогировать
}
```

## Таймаут: третий участник select

Функция `time.After(d)` возвращает канал, в который через время `d` придёт значение (пакет `time` подробно — в следующей секции, но этот паттерн нужен уже сейчас):

```go
select {
case result := <-slowWork:
	fmt.Println("успели:", result)
case <-time.After(2 * time.Second):
	fmt.Println("таймаут: работа заняла слишком долго")
}
```

Кто первый — тот и выиграл: пришёл результат раньше — берём его, истекло время — уходим с таймаутом. Три строчки — и никакая медленная операция не подвесит программу навсегда.

## Собираем всё: вежливый потребитель

```go
func consume(data <-chan int, quit <-chan struct{}) {
	for {
		select {
		case v, ok := <-data:
			if !ok {
				fmt.Println("данные кончились")
				return
			}
			fmt.Println("обработали", v)
		case <-quit:
			fmt.Println("попросили остановиться")
			return
		}
	}
}
```

Цикл `for` + `select` — рабочая лошадка конкурентного Go: горутина крутится, реагируя на то, что случилось первым. Заметьте `v, ok := <-data` прямо в ветке — закрытие канала тоже событие, и его обрабатывают так же.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| `make(chan int, 1000)` «на всякий случай» | маскирует проблемы: потребитель отстаёт, память растёт | размер из логики: N результатов → буфер N |
| считать, что полный буфер «выбрасывает» старое | отправка в полный буфер блокирует, ничего не выбрасывается | нужен сброс — неблокирующая отправка с default |
| `select` с default в цикле без другой работы | busy-loop: горутина жжёт процессор проверками | без default — пусть select блокируется |
| ветки на отправку И приём одного канала в одном select | путаница: сработать может любая | разделить ответственность: кто пишет, тот не читает |
| ждать порядка веток select («первая ветка главнее») | при нескольких готовых выбор случайный | нужен приоритет — проверяйте отдельным select до общего |
| `for { select {} }` без веток выхода | горутина-зомби живёт вечно | ветка quit-канала или закрытие data с return |

## Запомнить

- `make(chan T, n)` — канал с буфером на n значений: отправка блокирует только при полном буфере, приём — при пустом.
- `len(ch)` — сколько лежит сейчас, `cap(ch)` — ёмкость; порядок всегда FIFO.
- Буфер развязывает горутины по времени, но полный буфер блокирует — это отсрочка, не решение.
- `select` ждёт несколько операций с каналами; из готовых веток выполняется одна, при нескольких готовых — случайная.
- `default` делает select неблокирующим: «проверь и иди дальше».
- Таймаут: ветка `case <-time.After(d)` — кто раньше, тот и выиграл.
- `for` + `select` (+ ветка выхода) — стандартный каркас горутины-обработчика.
