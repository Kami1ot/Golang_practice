# context — вежливая просьба остановиться

Запускать горутины вы умеете. А останавливать? Пользователь закрыл вкладку, запрос отвалился по времени, программа завершается — работающие горутины надо как-то известить: «результат больше не нужен, сворачивайтесь». Прибить горутину снаружи в Go нельзя — намеренно: она могла бы бросить данные в неконсистентном состоянии. Вместо этого — стандартный механизм вежливой отмены: пакет `context`.

## Идея: сигнал отмены как канал

Вы уже знаете всё, чтобы собрать отмену вручную, — канал и select:

```go
quit := make(chan struct{})

go func() {
	for {
		select {
		case job := <-jobs:
			process(job)
		case <-quit: // закрыли канал — просыпаются ВСЕ, кто его слушал
			return
		}
	}
}()

close(quit) // просим остановиться
```

Помните: приём из закрытого канала не блокирует. Закрыл один — услышали все. Паттерн рабочий, но у каждого автора он свой: у одного канал зовётся `quit`, у другого `done`, у третьего своя сигнатура. Пакет `context` — этот же паттерн, стандартизированный для всей экосистемы Go.

## context.Context и его Done

Контекст (*context*) — «пропуск» с условиями работы: не отменили ли задачу и сколько времени осталось. Ключевые методы:

```go
ctx.Done() // <-chan struct{}: канал, который ЗАКРОЕТСЯ при отмене
ctx.Err()  // почему отменили: nil, пока живы
```

Корневой контекст — «никогда не отменят»:

```go
ctx := context.Background()
```

От него порождают отменяемые:

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel() // отпустить ресурсы контекста при любом выходе
```

`WithCancel` возвращает пару: контекст и функцию отмены. Вызвали `cancel()` — канал `ctx.Done()` закрылся, `ctx.Err()` стал возвращать `context.Canceled`.

```go
ctx, cancel := context.WithCancel(context.Background())

fmt.Println(ctx.Err()) // <nil> — пока живы

cancel()

fmt.Println(ctx.Err()) // context canceled
<-ctx.Done()           // не блокирует: канал уже закрыт
```

> [!NOTE]
> `defer cancel()` пишут ВСЕГДА, даже если отмена «и так произойдёт»: не вызванный cancel держит ресурсы контекста (таймеры, горутины уведомлений). go vet напоминает об этом предупреждением.

## Горутина, уважающая контекст

Рабочая лошадка — знакомый `for` + `select`, где одна из веток слушает `Done`:

```go
func worker(ctx context.Context, jobs <-chan int) {
	for {
		select {
		case job, ok := <-jobs:
			if !ok {
				return // задачи кончились
			}
			process(job)
		case <-ctx.Done():
			fmt.Println("останавливаюсь:", ctx.Err())
			return
		}
	}
}
```

Горутина реагирует на то, что случится раньше: новая задача или сигнал отмены. Именно так пишут все долгоживущие горутины в настоящих сервисах — иначе они превращаются в утечки: работают вечно на никому не нужный результат.

## WithTimeout: отмена по часам

Частный случай отмены — «дольше N не ждём»:

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

select {
case result := <-slowQuery:
	fmt.Println("успели:", result)
case <-ctx.Done():
	fmt.Println("не успели:", ctx.Err()) // context deadline exceeded
}
```

Через две секунды контекст отменится сам: `Done` закроется, `Err` вернёт `context.DeadlineExceeded`. Есть и `WithDeadline` — то же, но с конкретным моментом времени вместо длительности. Обратите внимание: две причины отмены различимы по ошибке — `context.Canceled` (отменили руками) и `context.DeadlineExceeded` (время вышло). Сравнивают их, конечно, через `errors.Is` — привет секции про ошибки.

## Дерево контекстов

Контексты образуют дерево: из `Background` вырастает контекст запроса, из него — контекст обращения к базе… Отмена родителя отменяет **всех потомков**:

```go
parent, cancelParent := context.WithCancel(context.Background())
child, cancelChild := context.WithCancel(parent)
defer cancelChild()

cancelParent()

<-child.Done() // ребёнок тоже отменён
fmt.Println(child.Err()) // context canceled
```

Так одно действие — «клиент отключился» — гасит целое дерево работ: и запрос к базе, и походы во внешние API, и все горутины между ними. Обратное неверно: отмена ребёнка родителя не трогает.

## Конвенции: как context живёт в коде

Экосистема Go договорилась о правилах — их проверяют на код-ревью:

- контекст — **первый параметр** функции, имя — `ctx`: `func Fetch(ctx context.Context, url string) error`;
- контекст **не хранят** в полях структур — передают явно по цепочке вызовов;
- `nil`-контекст не передают: нет осмысленного — берите `context.Background()`;
- функция, получившая ctx, обязана уважать его отмену — или честно не принимать ctx вовсе.

Загляните в стандартную библиотеку: `http.NewRequestWithContext`, методы `database/sql` — контекст везде первый параметр. Ваш код на следующих уровнях будет выглядеть так же.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| горутина без ветки `<-ctx.Done()` | не реагирует на отмену: утечка и работа впустую | `select` с веткой Done в цикле |
| забыли `defer cancel()` | ресурсы контекста висят до конца программы; go vet ругается | defer сразу после With* |
| `ctx` последним параметром или в поле структуры | ломает конвенцию — код неожиданен для читателя | первый параметр, имя ctx |
| проверка `ctx.Err() != nil` в цикле вместо select | опрос вместо ожидания: горутина жжёт процессор | ждать `<-ctx.Done()` в select |
| перепутали Canceled и DeadlineExceeded | неверная реакция: таймаут лечится ретраем, отмена — нет | различать через `errors.Is(err, context.…)` |
| отмена ребёнка «чтобы остановить всё» | родитель и соседи живут дальше | отменять нужный уровень дерева |

## Запомнить

- `context` — стандартный механизм отмены: `Done()` — канал, закрывающийся при отмене; `Err()` — причина.
- `ctx, cancel := context.WithCancel(parent)`; `cancel()` отменяет; `defer cancel()` — всегда.
- `WithTimeout(parent, d)` отменится сам: `Err()` — `context.DeadlineExceeded`; ручная отмена — `context.Canceled`; различать через `errors.Is`.
- Горутина уважает отмену веткой `case <-ctx.Done(): return` внутри select.
- Отмена родителя гасит всех потомков; ребёнок родителя не трогает.
- Конвенции: ctx — первый параметр с именем ctx, не хранится в структурах, не бывает nil.
