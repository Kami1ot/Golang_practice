# net/http: клиент — программа выходит в сеть

До сих пор ваши программы разговаривали сами с собой: терминал, файлы, память. Но самые интересные данные живут в сети: курсы валют, прогноз погоды, любое API. Всё это раздаётся по протоколу HTTP — и в Go для походов за данными не нужны сторонние библиотеки: пакет `net/http` из стандартной поставки умеет всё. А главное — вы уже знаете его строительные блоки: `io.Reader`, ошибки, JSON и таймауты. Осталось собрать их вместе.

## Минутка теории: как устроен HTTP

HTTP — протокол «запрос → ответ» (*request → response*): клиент спрашивает, сервер отвечает. В запросе (*request*):

- **метод** (*method*) — что сделать. `GET` — «дай данные», `POST` — «прими данные». Методов больше, но эти два — девяносто процентов работы;
- **URL** — у кого и что просим;
- **заголовки** (*headers*) — служебные поля: тип содержимого, авторизация…;
- **тело** (*body*) — данные; у GET его обычно нет, у POST — есть.

В ответе (*response*):

- **статус-код** (*status code*) — итог тремя цифрами: `200` — успех, `404` — не найдено, `500` — сервер сломался;
- заголовки — например, `Content-Type: application/json`: «в теле — JSON»;
- тело — сами данные.

```
GET /users/7 HTTP/1.1     →     HTTP/1.1 200 OK
Host: api.example.com           Content-Type: application/json

                                {"id":7,"name":"Гоша"}
       запрос                          ответ
```

## http.Get: один вызов — и вы в сети

```go
resp, err := http.Get("https://api.example.com/users/7")
if err != nil {
	return err // до сервера не добрались
}
defer resp.Body.Close()
```

`http.Get` возвращает пару: `*http.Response` и ошибку. И здесь — главная ловушка уровня. Ошибка означает «**не смогли достучаться**»: опечатка в адресе, DNS не знает такого имени, сервер выключен, сеть пропала. А вот если сервер *ответил* — хоть `200`, хоть `404`, хоть `500` — вызов **успешен**: `err == nil`, ответ лежит в `resp`.

> [!WARNING]
> `404 Not Found` — НЕ ошибка с точки зрения `http.Get`! Сервер честно ответил: «такого нет» — доставка сработала. `err != nil` — только про проблемы доставки. Забудете проверить статус — программа радостно распарсит страницу «не найдено» как данные.

## resp.Body — старый знакомый

Тело ответа — `resp.Body` типа `io.ReadCloser`. Раскроем: это `io.Reader` с уровня про потоки **плюс** метод `Close`. Тело не лежит в памяти готовой строкой — оно дочитывается из соединения по мере чтения. Читается как любой Reader — например, целиком через `io.ReadAll`:

```go
data, err := io.ReadAll(resp.Body)
if err != nil {
	return err // сеть оборвалась на середине
}
fmt.Println(string(data)) // тело строкой
```

А `Close` — обязательный ритуал. Незакрытое тело — удержанное соединение: Go не может вернуть его в пул переиспользования и открывает новые. Одиночный скрипт этого не заметит, сервис с тысячами запросов — захлебнётся.

```go
resp, err := http.Get(url)
if err != nil {
	return err
}
defer resp.Body.Close() // сразу после проверки ошибки
```

> [!NOTE]
> Порядок именно такой: сначала проверка `err`, потом `defer`. Пока `err != nil`, `resp` может быть `nil` — и `resp.Body.Close()` уронит программу паникой. Тот же рефлекс, что с файлами: открыл → проверил → `defer Close`.

## Проверяем статус

Код ответа лежит в `resp.StatusCode` — обычный `int`. Сравнивать можно с числом, но у `net/http` есть именованные константы — код с ними читается сам:

```go
if resp.StatusCode != http.StatusOK { // StatusOK == 200
	return fmt.Errorf("неожиданный статус: %d", resp.StatusCode)
}
```

Это идиома: не тот статус → вернуть ошибку, и обязательно **с кодом** — тому, кто будет читать логи, «что-то пошло не так» не поможет, а «неожиданный статус: 503» — вполне.

Частые статусы, которые стоит узнавать в лицо:

| Код | Константа | Смысл |
|---|---|---|
| 200 | `http.StatusOK` | успех, в теле — данные |
| 201 | `http.StatusCreated` | создано (типичный ответ на POST) |
| 400 | `http.StatusBadRequest` | сервер не понял ваш запрос |
| 401 | `http.StatusUnauthorized` | нужна авторизация |
| 404 | `http.StatusNotFound` | такого ресурса нет |
| 500 | `http.StatusInternalServerError` | сервер сломался |
| 503 | `http.StatusServiceUnavailable` | сервер перегружен, зайдите позже |

Первая цифра — категория: `2xx` — успех, `4xx` — «проблема на вашей стороне», `5xx` — «на нашей».

## JSON-ответ: прямая стыковка с прошлым уровнем

API отвечают JSON'ом, а `resp.Body` — это `io.Reader`. Ничего не напоминает? `json.NewDecoder` принимает ровно его — декодируем прямо из тела, без промежуточного `ReadAll`:

```go
type User struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

func FetchUser(url string) (User, error) {
	resp, err := http.Get(url)
	if err != nil {
		return User{}, err
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return User{}, fmt.Errorf("неожиданный статус: %d", resp.StatusCode)
	}

	var u User
	if err := json.NewDecoder(resp.Body).Decode(&u); err != nil {
		return User{}, err
	}
	return u, nil
}
```

Запомните этот каркас: запрос → проверка ошибки → `defer Close` → проверка статуса → декодирование. Восемь из десяти функций-клиентов в настоящих проектах выглядят именно так.

## POST: теперь отправляем сами

`http.Post` принимает три аргумента: URL, тип содержимого и тело-`io.Reader`:

```go
u := User{Name: "Гоша"}

data, err := json.Marshal(u) // структура → []byte
if err != nil {
	return err
}

resp, err := http.Post(url, "application/json", bytes.NewReader(data))
if err != nil {
	return err
}
defer resp.Body.Close()
```

`bytes.NewReader(data)` заворачивает байты в читателя — как `strings.NewReader` заворачивал строку. Второй аргумент уезжает в заголовок `Content-Type`: по нему сервер понимает, что в теле JSON, а не картинка. На успешный POST серверы часто отвечают не `200`, а `201 Created` — ещё одна причина проверять статус, а не «просто не ошибку».

## Клиент с таймаутом: не ждать вечно

Сюрприз: `http.Get` — это сокращение для `http.DefaultClient.Get`, а у клиента по умолчанию **нет таймаута**. Сервер принял соединение и молчит — ваша программа висит. Час. Сутки. Навсегда. Для скрипта-однодневки терпимо, для чего-то серьёзного — нет. Лечится своим клиентом:

```go
client := &http.Client{Timeout: 5 * time.Second}

resp, err := client.Get(url) // дольше 5 секунд не ждём
if err != nil {
	return err // здесь окажется и ошибка таймаута
}
defer resp.Body.Close()
```

Один такой клиент создают на всю программу и переиспользуют — он потокобезопасен. А «взрослый» способ управлять временем вы уже знаете — `context`. Для отмены конкретного запроса есть `http.NewRequestWithContext`:

```go
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
// ...
resp, err := client.Do(req) // отменится вместе с ctx
```

Пока достаточно знать, что это существует: `Timeout` у клиента закрывает большинство бытовых случаев.

## httptest: настоящий сервер без интернета

Как проверять HTTP-код тестами — ходить в реальный интернет? Ненадёжно: сеть моргает, API меняются. Стандартная библиотека предлагает лучше: `httptest.NewServer` поднимает **настоящий** HTTP-сервер на локальном адресе и отдаёт его URL:

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
)

func main() {
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, `{"answer":42}`) // так сервер отвечает на любой запрос
	}))
	defer srv.Close()

	resp, err := http.Get(srv.URL) // URL вида http://127.0.0.1:55123
	if err != nil {
		fmt.Println("не достучались:", err)
		return
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Println(resp.StatusCode)  // 200
	fmt.Println(string(body))     // {"answer":42}
}
```

Серверную часть — `http.HandlerFunc` и `w`/`r` — мы разберём отдельно; пока читайте её как «сервер, который отвечает вот этим». Важно другое: это не заглушка, запрос честно уходит по TCP на локальный адрес и возвращается. **Именно так проверяются задачи этого уровня**: тесты поднимают httptest-сервер и передают его URL вашим функциям — интернет не нужен вовсе.

## Типичные ошибки новичка

| Код | Что случится | Как чинить |
|---|---|---|
| нет `defer resp.Body.Close()` | утечка соединений: пул не переиспользуется, дескрипторы копятся | закрывать всегда, даже если тело не читали |
| `if err != nil` — и всё, статус не смотрим | 404 и 500 маскируются под успех, парсим мусор | после проверки err — проверка `resp.StatusCode` |
| `defer resp.Body.Close()` ДО проверки err | при ошибке `resp == nil` — паника nil pointer | сначала `if err != nil`, потом defer |
| прочитали Body дважды | второй `ReadAll` вернёт пустоту: поток уже выпит | читать один раз; нужно дважды — сохранить в переменную |
| клиент без `Timeout` | молчащий сервер подвешивает программу навсегда | `&http.Client{Timeout: 5 * time.Second}` |
| в ошибке нет кода статуса | по логам не понять, что ответил сервер | `fmt.Errorf("неожиданный статус: %d", resp.StatusCode)` |

## Запомнить

- `http.Get(url)` → `*http.Response` + ошибка. Ошибка — «не достучались»; `404`/`500` — НЕ ошибка, это успешно доставленный ответ.
- `resp.Body` — `io.ReadCloser`: читать как Reader (`io.ReadAll`, Decoder), закрыть обязательно: `defer resp.Body.Close()` сразу после проверки err.
- Статус — `resp.StatusCode`; сравнивать с константами `http.StatusOK`, `http.StatusCreated`…; не тот статус → ошибка с кодом в тексте.
- JSON-ответ: `json.NewDecoder(resp.Body).Decode(&v)` — тело уже Reader, промежуточный ReadAll не нужен.
- `http.Post(url, "application/json", bytes.NewReader(data))` — тело из `json.Marshal`; успех POST — часто `201`.
- Клиент по умолчанию не имеет таймаута: в серьёзном коде — `&http.Client{Timeout: …}`, точечно — `http.NewRequestWithContext`.
- `httptest.NewServer` поднимает настоящий локальный сервер для тестов — так проверяются и задачи уровня.
